# 通用 Skill 二开流程

## 1. 目的与适用范围

本流程用于把一个用户有权使用和改造的已有 Skill，开发成定位、工作流、内容、测试、文档和发布身份均独立的新 Skill。它也适用于从多个参考 Skill 中提炼机制，再开发一个新 Skill。

它解决的是一条完整产品链路：

```text
立项 → 隔离参考源 → 学习与审计 → 独立定位 → 规划 → 开发
     → 文档 → 静态验证 → 隔离前向测试 → 安装 → 发布审计
     → GitHub 发布 → 使用反馈与迭代
```

本流程不预设原 Skill 的题材、功能和实现形式。对话型、工具型、内容生成型、代码工作流型和带脚本的 Skill 均可使用。

## 2. 核心原则

### 2.1 学习机制，不延续产品身份

参考 Skill 只作为私有输入。允许学习它解决的问题、有效机制、资源组织和失败边界，但新 Skill 必须重新决定：

- 名称和公共身份；
- 目标用户和核心问题；
- 触发与不触发条件；
- 工作流、输入输出和停止条件；
- 默认值、示例、表达方式和品牌；
- 测试与发布声明。

只改名称、作者、颜色或 README，不算有效二开。

### 2.2 先形成产品决策，再写 `SKILL.md`

不要把参考 Skill 的文件顺序直接改写成新 Skill。先回答“为谁解决什么问题、何时触发、做到什么算成功、哪些事明确不做”，再决定运行包结构。

### 2.3 评估、运行、用户和测试文档分层

- 评估和研发决策放在仓库 `docs/`；
- Agent 运行指令放在 `SKILL.md`；
- 用户用途和调用方式放在 `README.md`；
- 详细规则按需放在 `references/`；
- 测试证据放在 `tests/` 和 `docs/forward-tests/`；
- 不把来源对比、授权证明或私有溯源材料放进公共仓库。

### 2.4 所有能力声明都需要证据

不得虚构：

- 已完成的功能；
- 自动发布、后台运行或持久化能力；
- 性能、用户数、下载量和平台效果；
- 已通过但实际没有执行的测试；
- 对外部工具、服务和权限的控制能力。

### 2.5 复杂 Skill 必须做隔离前向测试

静态校验只能证明文件和显式契约存在，不能证明一个新 Agent 在真实请求下会正确触发、执行和退出。复杂 Skill 发布前必须使用新任务或新 Agent，以接近真实用户的输入测试。

## 3. 阶段一：立项与边界确认

### 3.1 确认输入和授权边界

记录但不公开：

- 参考 Skill 的本地路径或来源；
- 用户说明的授权、署名和许可证义务；
- 哪些素材可以修改、复用或发布；
- 哪些材料只能用于内部学习。

如果用户明确给出署名、许可证或命名义务，必须保留。没有明确要求时，也不能擅自发布来源档案和比较笔记。

### 3.2 确认目标仓库与 Skill 目录

新 Skill 使用独立顶层目录：

```text
<repository>/<skill-name>/
```

名称规则：

- 只用小写字母、数字和连字符；
- 少于 64 个字符；
- 优先使用简短、动词导向、能够说明动作的名称；
- 文件夹名称必须和 front matter 中的 `name` 一致。

### 3.3 隔离参考源和公共仓库

参考源应放在一次性或私有目录，不要直接把原仓库变成公共工作区。如果复制了 Git 仓库，在任何编辑或提交前：

1. 确认准确目标目录；
2. 删除根目录和嵌套目录中的 `.git`；
3. 初始化新的 `main` 仓库；
4. 不保留原远程、tag、branch、reflog 和 commit object；
5. 不创建“原版快照”或“迁移前基线”提交。

首个公共提交应该是完成后的独立版本，而不是来源版本。

### 本阶段交付物

- 明确的工作目录和目标仓库；
- 非公开的授权与来源记录；
- 干净的 Git 起点；
- 初步项目任务和下一步。

### 退出门禁

- 目标目录无歧义；
- 公共仓库不包含来源 Git 历史；
- 用户明确提出的署名或许可证义务已记录；
- 新 Skill 尚未开始沿用来源品牌和定位。

## 4. 阶段二：学习与源能力审计

### 4.1 先检查能力清单

在自行设计之前，确认是否存在适用的：

- `skill-creator`；
- 授权二开工作流；
- 领域 Skill；
- GitHub、浏览器、文档或测试工具；
- 项目管理和知识管理工具。

只选择能直接支持当前任务的最小能力组合。

### 4.2 审计参考 Skill

至少检查：

- front matter、触发词和不触发边界；
- 用户输入、输出和中间状态；
- 完整工作流和停止条件；
- `references/`、`scripts/`、`assets/`；
- 工具、API、环境和第三方依赖；
- 示例、测试、fixture 和预期结果；
- 作者、邮箱、域名、仓库、签名、页脚和包元数据；
- 许可证、copyright 和署名信息；
- 运行时没有实现但文档声称存在的能力；
- 隐私、安全、持久化和破坏性操作风险。

### 4.3 生成三类决策

对每项能力归类：

#### 保留为能力

值得继续解决的用户问题或可验证机制。保留的是能力目标，不是来源文案和产品身份。

#### 实质重建

需要根据新定位重新设计的部分，例如触发条件、工作流、模式、输出协议、工具交互、默认值、错误处理和示例。

#### 完全删除

与新产品无关、无法验证、存在风险、只有品牌价值或会扩大范围的内容。

### 本阶段交付物

- 私有来源审计或转换简报；
- 能力清单；
- 依赖和风险清单；
- 保留、重建、删除三类决策。

### 退出门禁

- 已理解来源 Skill 实际能做什么，而不只看 README；
- 已识别未经实现的能力声明；
- 已识别身份、许可证和 Git 残留；
- 已能在不引用来源品牌的情况下描述要解决的问题。

## 5. 阶段三：独立产品定义与评估文档

### 5.1 建立独立产品定义

至少明确：

- 一句话定位；
- 目标用户；
- 核心需求；
- 成功结果；
- 应触发场景；
- 不应触发场景；
- 输入契约；
- 输出契约；
- 审批点和停止条件；
- 默认行为；
- 工具和数据边界；
- 当前版本包含与不包含的内容。

### 5.2 用具体用户请求定义边界

不要只写抽象描述。至少准备以下类型的请求：

- 典型正向请求；
- 模糊但应该触发的请求；
- 极简输入；
- 信息缺失输入；
- 接近边界但不应该触发的请求；
- 应路由给其他 Skill 的请求；
- 工具不可用或权限不足的请求；
- 取消、失败、暂停或部分完成请求；
- 隐私或持久化相关请求；
- 可能导致破坏性操作的请求。

### 5.3 评估必须落地

在仓库创建或更新：

```text
docs/evaluations/<skill-name>.md
```

评估文档至少包含：

- 基本信息和当前阶段；
- 评估结论；
- 定位与用户需求；
- 触发和不触发边界；
- 保留、重建、删除决策；
- 核心流程和目录规划；
- 当前版本包含与不包含；
- 风险与约束；
- 验收场景和指标；
- 实施状态、下一步和更新记录。

同一个 Skill 后续评估继续更新同一份文档，不为每轮讨论创建互相割裂的文件。

### 本阶段交付物

- 完整评估文档；
- 独立产品定位；
- 版本范围；
- 初始验收场景。

### 退出门禁

- 新产品能脱离来源 Skill 独立说明；
- 触发、退出和路由边界清楚；
- 当前版本不包含的能力已经明确；
- 所有关键产品判断已进入评估文档。

## 6. 阶段四：运行包与资源规划

### 6.1 选择合适的自由度

- 多种答案均合理、依赖上下文判断：用文本规则和启发式，高自由度；
- 有推荐模式但允许参数变化：用伪代码、模板或参数化脚本，中自由度；
- 操作脆弱、顺序固定、错误代价高：使用确定性脚本和严格校验，低自由度。

### 6.2 规划目录

通用结构：

```text
<skill-name>/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
├── scripts/       # 仅在需要确定执行时创建
├── references/    # 仅在需要按需读取细节时创建
└── assets/        # 仅在输出需要复用文件时创建
```

本仓库要求每个 Skill 都包含用户版 `README.md`。其他辅助文档不要堆进运行目录。

### 6.3 判断资源类型

#### 使用 `scripts/`

适用于：

- 同一代码会被反复生成；
- 结果必须确定；
- 文件转换、解析或校验容易出错；
- 工具调用顺序需要固化。

新增脚本必须实际运行，并为关键逻辑补测试。

#### 使用 `references/`

适用于：

- API、schema、政策、术语和领域知识；
- 大量示例或变体；
- 非每次运行都需要的详细流程。

`SKILL.md` 必须说明何时读取每个 reference。超过 100 行的 reference 应包含目录。避免 references 之间层层跳转。

#### 使用 `assets/`

适用于：

- 输出需要复制或修改的模板；
- 图片、图标、字体；
- HTML、React 或文档样板；
- 不是给 Agent 阅读，而是给最终产物使用的文件。

### 6.4 渐进披露

按三层组织上下文：

1. `name + description`：常驻，用于判断是否触发；
2. `SKILL.md`：触发后加载，只保留核心流程；
3. `references/scripts/assets`：按需读取或执行。

不要在 `SKILL.md`、README 和 references 中重复维护同一内容。

### 本阶段交付物

- 运行包目录设计；
- scripts、references、assets 清单；
- 测试策略；
- 文档分层方案。

### 退出门禁

- 每个文件都有明确运行用途；
- 没有为了形式创建空目录；
- 详细内容有按需加载路径；
- 易错重复操作已经考虑确定性脚本。

## 7. 阶段五：开发实现

### 7.1 创建骨架

使用仓库脚手架或 `skill-creator` 的初始化脚本创建目录，不手工复制旧 Skill 作为最终骨架。

### 7.2 先开发可复用资源

优先完成：

- 确定性脚本；
- reference 资料；
- 输出模板和 assets；
- schema 和示例 fixture。

这样可以让 `SKILL.md` 引用真实存在的资源，而不是先写出无法执行的流程。

### 7.3 编写 `SKILL.md`

front matter 只包含：

```yaml
---
name: <skill-name>
description: <能力、触发场景和关键边界>
---
```

`description` 是主要触发入口，应同时说明：

- Skill 能做什么；
- 什么请求应该使用；
- 关键不触发场景。

正文使用祈使句，重点写：

- 核心工作流；
- 分支判断；
- 工具调用和审批点；
- 输入输出契约；
- 停止和失败条件；
- 何时读取 references；
- 不可虚构的能力边界。

尽量控制在 500 行以内。详细领域信息和大量示例移入 references。

### 7.4 编写用户 README

README 至少说明：

- 这个 Skill 有什么用；
- 适合和不适合什么情况；
- 如何安装和调用；
- 常用调用示例；
- 会产生什么结果；
- 使用什么工具或数据；
- 能力、隐私和持久化边界。

README 面向用户，`SKILL.md` 面向 Agent，两者表达可以不同，但事实不能冲突。

### 7.5 生成 UI 元数据

`agents/openai.yaml` 应与当前 Skill 一致，至少包含：

- `display_name`；
- `short_description`；
- 显式包含 `$<skill-name>` 的 `default_prompt`。

Skill 大改后重新检查 UI 元数据，避免界面描述仍停留在旧版本。

### 7.6 清除占位和来源内容

开发结束前检查：

- TODO 和示例占位；
- 来源作者、仓库、域名和品牌；
- 旧触发词、旧包名和旧目录名；
- 未使用资源和空目录；
- 测试 fixture 中的来源身份；
- README、UI 和运行指令之间的冲突。

### 本阶段交付物

- 完整运行包；
- 用户 README；
- UI 元数据；
- 必要脚本、references、assets 和 fixture。

### 退出门禁

- 运行包可以脱离来源目录工作；
- 所有引用文件真实存在；
- 用户文档和运行行为一致；
- 没有占位符、无用文件和未实现声明。

## 8. 阶段六：静态、单元和集成验证

### 8.1 结构校验

运行仓库校验和 `quick_validate.py`，检查：

- front matter 格式；
- name、文件夹和 UI 名称一致性；
- 必需文件；
- `default_prompt` 是否包含 `$<skill-name>`；
- 引用路径是否存在；
- 运行包是否含有禁止的旁支文档和临时文件。

### 8.2 测试行为契约

测试应覆盖共享行为和发布风险，而不仅是文件存在：

- 触发和误触发边界；
- 核心工作流；
- 输入缺失和异常分支；
- 工具不可用和权限不足；
- 停止、取消和部分成功；
- 输出格式和关键字段；
- 数据、隐私和持久化；
- UI 和 README 一致性；
- 源身份和占位残留。

### 8.3 实际执行脚本和样例

- 每个新增的关键脚本都要运行；
- 至少用一个完整真实输入生成结果；
- 检查用户可见输出，不只检查 exit code；
- 文档、图片、网页或演示文稿等视觉产物还要进行视觉检查。

### 8.4 不为通过而弱化测试

如果来源 fixture 被删除，应换成用户自己的 fixture，并保持等价行为覆盖。不要因为新实现无法通过就降低验收标准。

### 本阶段交付物

- 自动化测试；
- 测试通过记录；
- 完整样例输出；
- 修复后的评估实施状态。

### 退出门禁

- 仓库测试通过；
- `quick_validate.py` 通过；
- 新增脚本已实际运行；
- 至少一个完整样例经过人工检查。

## 9. 阶段七：隔离前向测试与迭代

### 9.1 建立测试矩阵

前向测试数量按复杂度和风险确定，不固定为某个数字。至少覆盖：

- 典型成功路径；
- 模糊输入；
- 最少输入；
- 信息缺失；
- 不应触发；
- 应路由其他 Skill；
- 失败、取消或部分完成；
- 工具不可用；
- 权限、隐私和持久化边界；
- 可能产生高成本或破坏性影响的路径。

### 9.2 使用全新上下文

每个隔离测试使用新的 Agent 或任务。推荐提示格式：

```text
Use $<skill-name> at /absolute/path/to/<skill-name> to respond to this user request:
“<真实用户请求>”
Respond exactly as the assistant would to the user.
```

不要告诉测试 Agent：

- 预期答案；
- 怀疑的 bug；
- 刚修改的规则；
- 通过条件和诊断结论。

否则测试验证的是提示泄漏，而不是 Skill 的可迁移行为。

### 9.3 由开发者独立判定

测试 Agent 只生成用户可见结果。开发者依据事先写好的验收标准检查：

- 是否正确触发或退出；
- 是否遵守工作流和审批点；
- 是否使用了真实工具；
- 是否产生虚假能力声明；
- 是否满足输出契约；
- 是否造成不必要的副作用。

### 9.4 失败后闭环

每个失败都要：

1. 记录输入、观察结果和失败原因；
2. 判断应修改 `SKILL.md`、reference、script、测试还是产品范围；
3. 做最小必要修订；
4. 同步更新静态测试；
5. 使用新的隔离 Agent 复测；
6. 检查修改是否破坏其他场景。

### 9.5 落地前向测试报告

创建：

```text
docs/forward-tests/<skill-name>-<version>.md
```

至少记录：

- 测试对象和安装位置；
- 测试方法；
- 场景和判定口径；
- 观察到的行为；
- 通过或失败；
- 修订和复测；
- 最终结论。

### 本阶段交付物

- 隔离测试矩阵；
- 原始输出或可审计摘要；
- 前向测试报告；
- 失败修订和复测证据。

### 退出门禁

- 关键正向、负向和边界场景都已覆盖；
- 失败项完成修订和全新上下文复测；
- 测试结论已落地文档；
- 没有依赖对话泄漏才能通过的场景。

## 10. 阶段八：干净安装和能力登记

### 10.1 安装干净副本

把最终运行目录复制或链接到：

```text
~/.codex/skills/<skill-name>
```

如果目标已存在，先确认它是否包含用户改动，不得无条件覆盖。

### 10.2 验证安装副本

- 对安装目录再次运行 `quick_validate.py`；
- 比较仓库运行目录和安装目录；
- 从新任务调用 Skill；
- 确认没有依赖仓库外的临时文件；
- 如果使用脚本或 assets，验证安装后的相对路径仍然有效。

### 10.3 刷新能力清单

安装、更新或删除 Skill 后，刷新：

```text
~/.codex/agent-capabilities.md
~/.codex/agent-capabilities.json
```

确认能力名称、说明、示例和安装路径正确。

### 本阶段交付物

- 可被 Codex 发现的安装副本；
- 安装目录验证结果；
- 更新后的全局能力清单。

### 退出门禁

- 安装目录与发布候选一致；
- 新任务可以发现并调用；
- 不依赖开发目录中的临时资源；
- 能力清单已更新。

## 11. 阶段九：发布前审计

### 11.1 身份和来源残留扫描

扫描整个公共仓库，而不只扫描 Skill 目录：

- 来源作者、别名、邮箱和签名；
- 来源 Skill、包、仓库和域名；
- `author`、`maintainer`、`homepage`、`repository`、`funding` 等字段；
- 图片、PDF、Office、压缩包和生成文件的元数据；
- 文件名、示例、fixture 和迁移脚本；
- license 和 copyright。

通用 URL、依赖许可证和标准链接需要人工复核，不应机械删除。

### 11.2 Git 审计

发布独立首版时确认：

```bash
find . -name .git -print
git log --all --oneline
git remote -v
git tag --list
git fsck --full --unreachable
```

预期：

- 只有项目根目录的 `.git`；
- 没有来源 commit；
- 只有目标 `origin`；
- 没有来源 tag 和 branch；
- 提交作者和邮件属于目标项目；
- 没有保留来源不可达对象。

### 11.3 公共一致性检查

以下位置必须使用同一个名称、版本和能力边界：

- `SKILL.md`；
- `README.md`；
- `agents/openai.yaml`；
- 示例和截图；
- 仓库描述；
- 包元数据；
- 安装说明；
- 测试和发布说明。

公共文档只描述当前独立产品。除非用户要求，不公开“从什么 Skill 改名、迁移或重建”的过程。

### 11.4 最终验证

- 完整测试再次通过；
- 工作区无意外修改；
- 暂存文件只有本次发布内容；
- Git 空白和 trailing whitespace 检查通过；
- 目标远端确实是用户的新仓库。

### 本阶段交付物

- 残留审计结果；
- Git 历史和远程检查结果；
- 最终发布候选。

### 退出门禁

- 无禁止公开的来源身份和私有路径；
- Git 历史干净；
- 公共身份一致；
- 测试和安装证据完整；
- 工作区和暂存范围清楚。

## 12. 阶段十：GitHub 发布与远端验收

### 12.1 创建独立首个提交

首个提交应包含可发布的独立版本，例如：

```text
Initial release of <skill-name> <version>
```

不提交来源原版快照和中间迁移历史。

### 12.2 推送目标仓库

- 目标仓库应为空或确认没有无关用户内容；
- 推送 `main`；
- 如果用户要求正式版本，再创建版本 tag；
- 不保留来源 `upstream`。

如果来源历史已经被推到目标远端，不应只依赖 force push。需要删除并重建远端仓库，再发布干净历史。

### 12.3 远端验收

推送后：

1. 检查远端 `main` SHA；
2. 查看提交作者和提交信息；
3. 检查 CI；
4. 从远端新鲜克隆；
5. 在克隆目录再次运行测试和残留审计；
6. 检查只有预期的 branch、tag 和 commit；
7. 确认工作区干净。

### 本阶段交付物

- GitHub 仓库和 commit；
- CI 结果；
- 新鲜克隆验证；
- 发布说明或 tag（如果需要）。

### 退出门禁

- 远端 SHA 与本地一致；
- CI 通过；
- 新鲜克隆可以独立验证；
- 远端没有来源历史或身份；
- 当前发布版本可以安装和调用。

## 13. 阶段十一：反馈、迭代和推广材料

### 13.1 收集真实使用证据

发布后记录：

- 什么请求成功触发；
- 什么请求误触发或没有触发；
- 哪个步骤需要重复解释；
- 哪些工具或权限经常失败；
- 用户输出是否符合预期；
- 哪些能力被频繁请求但当前版本没有。

不要因为单次建议立刻扩大范围。只有出现重复证据，再进入下一版本评估。

### 13.2 继续更新同一评估文档

每次版本变化都更新原有 `docs/evaluations/<skill-name>.md`：

- 新证据；
- 产品判断变化；
- 新版本范围；
- 新风险；
- 实施和测试结果；
- 更新记录。

### 13.3 生成衍生文档

按实际需求生成：

- 用户教程；
- 公众号或社交媒体材料包；
- 演示文稿；
- 发布说明；
- 维护和交接说明。

衍生材料必须以当前代码和测试事实为准，区分：

- 已验证产品事实；
- 作者真实经历；
- 作者判断；
- 候选观点；
- 发布前需要重新核对的时效信息。

推广材料不得把隔离 Agent 测试写成真实用户效果，也不得把计划能力写成已实现能力。

### 本阶段交付物

- 真实使用反馈；
- 更新后的评估记录；
- 下一版本候选；
- 必要的推广、教程和交接文档。

## 14. 文档产物总表

| 文档 | 默认位置 | 是否随 Skill 安装 | 作用 |
|---|---|---:|---|
| `SKILL.md` | `<skill-name>/SKILL.md` | 是 | Agent 运行指令 |
| 用户 `README.md` | `<skill-name>/README.md` | 是 | 用途、调用和边界说明 |
| UI 元数据 | `<skill-name>/agents/openai.yaml` | 是 | Skill 列表和默认提示 |
| 详细参考 | `<skill-name>/references/` | 是 | 按需加载的规则和知识 |
| 确定性脚本 | `<skill-name>/scripts/` | 是 | 稳定执行重复或脆弱操作 |
| 输出资产 | `<skill-name>/assets/` | 是 | 模板、图片、字体和样板 |
| 评估记录 | `docs/evaluations/<skill-name>.md` | 否 | 定位、范围、决策和状态 |
| 自动化测试 | `tests/` | 否 | 结构和行为契约验证 |
| 前向测试报告 | `docs/forward-tests/<skill-name>-<version>.md` | 否 | 隔离真实场景证据 |
| 仓库 README | `README.md` | 否 | 仓库导航和 Skill 索引 |
| 推广/教程材料 | MindDesk 或指定内容库 | 否 | 面向发布和传播的衍生内容 |

## 15. 何时可以跳过步骤

只有存在明确理由时才跳过，并在评估文档中记录：

- 没有参考 Skill、完全从零开发：可跳过来源身份清理，但不能跳过产品定义和测试；
- Skill 已有符合规范的目录：可跳过骨架初始化；
- 纯对话且无重复确定操作：可以不创建 `scripts/`；
- 没有详细领域知识：可以不创建 `references/`；
- 不生成可复用文件：可以不创建 `assets/`；
- 极简单、低风险 Skill：可以缩小前向测试矩阵，但至少要有典型正向和边界请求；
- 用户没有要求发布：可以暂不执行 GitHub 发布，但仍应完成本地验证和安装候选检查。

不能跳过：

- 授权和明确义务确认；
- 独立定位和触发边界；
- 评估文档；
- 基本结构校验；
- 未实现能力和来源残留检查；
- 与风险相称的真实请求验证。

## 17. 标准完成定义

一个 Skill 二开任务只有同时满足以下条件才算完成：

1. 产品定位和工作流已经独立，不是表面换名；
2. 评估和关键决策已经落地；
3. 运行包、README、UI 和必要资源完整；
4. 静态、自动化、样例和前向测试与风险相称；
5. 干净安装可以被新任务发现和调用；
6. 来源身份、Git 历史和公共声明完成审计；
7. 远端新鲜克隆能够独立通过验证；
8. 后续反馈入口和下一版本规则清楚。

达到这个标准，得到的不是一份修改过的提示词，而是一个可维护、可验证、可安装、可发布和可持续迭代的独立 Skill 产品。
