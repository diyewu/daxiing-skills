# pick-something-fun 评估记录

## 基本信息

- Skill 名称：`pick-something-fun`
- 中文工作名：选个好玩的
- 当前阶段：V0.1 已完成开发、验证与发布审计
- 最后更新：2026-08-13
- 评估对象：用户提供的本地活动推荐与计划原型，仅用于能力和结构评估

## 评估结论

值得重建为独立 Skill，但不应延续“大而全的活动推荐、个人档案、日历、邀请和 RSVP 管理器”定位。新版本聚焦一个更清楚的问题：当用户不知道现在、今晚或周末做什么时，根据现有约束快速选出一项真实可执行的活动；只有当地点、天气、营业时间、票务或场次会改变决定时，才查询并核验当前信息。

V0.1 采用纯对话和按需联网方案，不默认保存偏好、历史、联系人或群组资料，也不把创建日历、发送消息、邀请和提醒冒充为已经完成的动作。

## 定位与用户需求

- 一句话定位：一个低摩擦的活动决策 Skill，把“今天做什么”变成一个符合时间、地点、同行者、预算、精力和硬性限制的可执行方案。
- 目标用户：临时想安排休闲活动，但不想浏览大量榜单或完成一份问卷的人。
- 核心需求：减少选择成本，同时避免给出已经关门、天气不合适、超预算或不符合同行者限制的建议。
- 成功结果：在已有信息足够时直接给出一个首选；信息不足时只询问一个会改变决定的问题；涉及当前事实时提供可核验来源；最终让用户知道“做什么、为什么合适、如何开始、还有什么需要确认”。

## 触发场景与边界

### 应触发

- “今晚做点什么？”“周末有什么好玩的？”
- “约会不知道去哪。”“带孩子半天怎么安排？”
- “下雨了，三个人待在家里玩什么？”
- “预算 200 元，杭州，想找一个不太累的活动。”
- “别问了，直接替我选一个。”
- “给我三个方向，我自己比较。”
- 用户已经选中活动，希望把它整理成可执行的小计划。

### 不应触发

- 多日旅行路线、机酒和跨城市行程规划；
- 单纯查询某家餐厅、电影、游戏或景点的资料；
- 只要求创建日历、提醒、邀请或发送消息；
- 完整活动策划、婚礼、会议或大型聚会项目管理；
- 对已经明确的技术、工作或学习任务进行任务启动；
- 需要医疗、法律或高风险户外专业判断的请求。

不应触发时，直接处理用户真正的请求或路由到更合适的 Skill，不要强行生成活动卡。

## 重构决策

### 保留

- 用时间、地点、同行者、预算、精力和偏好约束活动选择；
- 支持临时决定、居家活动、约会、家庭、朋友和独自活动；
- 在天气、营业时间、场次、票务和当地活动等因素重要时查询当前信息；
- 把一个被接受的想法转成可执行计划。

### 重建

- 名称、公共定位、触发描述、语言风格和所有示例；
- 从固定问卷改为渐进收集约束，每轮最多问一个关键问题；
- 从“展示大量灵感”改为“给一个首选，并解释为什么适合”；
- 将创意生成、当前事实核验和外部行动拆成三个阶段；
- 为来源可信度、时效性、价格、距离和可用性增加明确边界；
- 将保存偏好、日历、提醒和消息改为明确授权、真实工具和结果确认；
- 建立不触发、转交、失败和停止条件。

### 删除

- 原型的公共身份、作者信息、平台元数据、品牌语言和个人示例；
- 平台专属目录、联系人渠道、定时工具和 API 命令；
- 默认创建用户档案、保存历史、推断偏好和维护群组资料；
- 带羞耻、催促、粗口和强迫感的表达；
- 未经工具执行就声称日历、提醒、邀请、消息或 RSVP 已完成；
- 固定要求每次都查询天气、给出多项备选、增加 wild card 或要求用户评价；
- 大量静态活动目录和虚构的当前电影、评分、场次、天气与商户数据。

## 核心产品设计

### 三种决策模式

1. `quick-pick`：信息足够或用户要求直接选，只给一个首选和一个降级备选。
2. `compare`：用户想比较时，给出最多三个差异明确的方案，不堆同质选项。
3. `shape-it`：信息不足时，每轮只问一个真正会改变推荐的问题，最多两轮后给出可修正方案。

模式由上下文推断，不要求用户配置。

### 最小约束模型

优先从对话中解析：

- 时间：现在、今晚、周末或具体时间段；
- 地点与可接受移动范围；
- 同行者和人数；
- 室内、室外或均可；
- 预算；
- 精力和活动强度；
- 硬性限制：饮食、无障碍、未成年人、宠物、交通和天气等。

只有缺失信息会显著改变方案、成本或安全时才提问。不得默认收集联系人、精确住址、健康状况和长期偏好。

### 选择流程

1. 判断是否应由本 Skill 处理。
2. 提取已有约束，确定 `quick-pick / compare / shape-it`。
3. 生成少量候选，先过滤硬性限制。
4. 比较可行性、摩擦、预算、时间、天气和新鲜感。
5. 只有当前事实会改变结果时才联网核验。
6. 输出一个可执行决策卡；备选必须解决不同取舍。
7. 用户接受后，给出最小执行步骤。
8. 只有用户明确要求、工具可用且确认具体内容后，才执行日历、提醒或消息等外部操作。

### 决策卡

```text
今天就选：
为什么合适：
怎么开始：
时间与预算：
出发前确认：
备选：
```

只保留有价值的字段。纯居家活动通常不需要地点、营业时间和来源；真实场馆和活动必须标明已核验事实及仍需确认的内容。

## 当前事实与工具边界

- 天气、营业时间、票务、价格、场次、活动日期、道路和流媒体可用性属于时效事实，应按需查询。
- 优先使用活动主办方、场馆官网、影院、票务方、官方天气或地图等直接来源。
- 搜索摘要、聚合榜单和用户评论只能辅助发现，不能单独证明仍在营业或仍有票。
- 无法核验时，明确写“需要出发前确认”，不得编造商户、评分、链接、票价和时间。
- 不因用户只说“今晚做什么”就默认知道其位置、日历、偏好和天气。
- 任何日历写入、购买、预订、提醒、邀请和消息发送都属于外部操作，必须获得明确授权并由真实工具成功完成。
- 默认不保存请求、偏好、联系人、历史和选择结果。

## 版本范围

### V0.1 包含

- 快速选择、比较选择和渐进澄清三种模式；
- 时间、位置、人数、预算、精力和硬限制解析；
- 居家、外出、独自、约会、家庭和朋友活动；
- 按需联网核验天气、营业时间、场次、票务、价格和当前活动；

- 多日旅行规划和大型活动项目管理；
- 专用 Google Places、流媒体、影院或票务 API 脚本；
- 固定活动目录和平台绑定。

### 后续候选

- 用户明确授权的本地偏好档案；
- 接受方案后的一次性日历和提醒组合；
- 可选的活动反馈与重复规避；
- 针对特定城市或数据源的确定性查询工具。

## 风险与约束

- 推荐很容易变成泛泛榜单，必须做出明确选择并解释取舍。
- 当前地点、天气、开放时间和票务随时变化，需要查询或明确未核验。
- 用户位置可能缺失或敏感，只收集做出决定所需的最低粒度。
- 预算不能只用 `$ / $$` 代替；没有真实价格时使用范围并标注估计。
- 不应把饮酒、高强度户外或夜间长距离驾驶作为默认选项。
- 儿童、无障碍、饮食、宠物和身体强度属于硬限制，不得用“惊喜”覆盖。
- 推荐不是预订；没有工具成功结果时不得写“已锁定”“已订好”“已通知”。
- 用户要的是快速决定时，不能用多轮问卷重新制造选择负担。

## 验收场景

1. 用户只说“今晚做什么”，已有位置上下文时直接给一个可修正首选，不启动问卷。
2. 用户没有位置且要求附近真实活动，只问位置或可接受范围，不编造本地场所。
3. 用户要求“不要问，直接选”，使用已有信息给一个首选并说明假设。
4. 用户想比较三个方案，选项应有明显的预算、强度或室内外差异。
5. 用户要求雨天居家三人活动，不查询无关地点和营业时间。
6. 用户要求今晚的电影场次，转入当前场次查询，而不是生成普通活动卡。
7. 用户要求三日旅行路线，路由到旅行规划，不把它压成休闲活动选择。
8. 用户给出儿童、饮食或无障碍限制，方案必须先满足硬限制。
9. 用户要求一家真实场馆，营业时间和活动日期需要来源；无法核验时明确说明。
10. 用户接受方案并要求加日历，但没有可用工具，不得声称已经创建事件。
11. 用户要求发送邀请，执行前必须确认对象和内容；没有工具时只提供可复制文本。
12. 用户未授权保存，Skill 不创建偏好、历史或联系人记录。

## 验收指标

- 已有信息足够时，第一条回复就给出可执行首选。
- 信息不足时，每轮最多一个关键问题，通常不超过两轮形成方案。
- 备选最多三个且解决不同取舍，不堆同质列表。
- 时效事实有来源或明确标记为未核验。
- 不编造地点、营业时间、评分、价格、场次、票务和链接。
- 不虚构保存、日历、提醒、消息、预订和后台执行。
- 不使用羞耻、催促、价值判断和压力型语言。
